# A filter's documentation lives on its parameter and a presence filter shows `true`

Consumers lint the document for a description and an example on every query parameter, and the projection let several filters reach it without either, or dropped what the author wrote. A filter's description and example now stay on the Parameter Object, never in its schema, while a declared default becomes the schema's `default`, the one place OAS gives it. A presence filter's value is ignored, so it takes `describedAs()` but no `example()`: its description always ends "Applied when present; value ignored." and its example is the string `true`, a string because its schema is one and the value travels as query text. A list filter's example and default are converted between its two parameters, members for an array schema and the delimiter-joined string where the delimited form is a string, so both show the same values and each validates against its own schema. A filter family's description and example go in its `x-filter-families` entry and on the shared `filter` parameter, the example being one full key and its value. A filter group child's description or example, and a relation builder's `example()`, would never reach the document, so they fail when the filter or field is built rather than vanish; a convenience filter's preset description is marked as such and doesn't count.

The same lint covers schema properties, so a relationship object's schema shows one member's linkage, built from the id the operation examples use, and every schema example is written as OAS 3.1's `examples` list, since the Schema Object's `example` is deprecated there.
