# Examples read counting and linkage ids from opt-in metadata

Two things an operation example needs were invisible to the projector. A paginator built with `withCount()` renders a total and a `last` link on every request, but nothing in the metadata or the page schema said so, so its examples showed a count-free page. Linkage to a type the server does not register had no id to show at all. Type and relation metadata may now implement `DeclaresAlwaysCounted`, set from the paginator's `wantsCount()`, and relation metadata `DeclaresRelationExampleId`, set from a new `exampleId()` on the core relation builder. Both are optional interfaces, as the earlier metadata additions are, so existing integrations compile and project unchanged, and neither touches the emitted schema, so the contract stays at the 13 it already is.

We kept counting out of the page schema's `x-paginator` extension, though the paginator could have described itself there, because that extension is structure every document carries and a new member would have moved the baseline contract for a fact only the examples use. An always-counting collection shows the total as the runtime renders it for one, in `meta.total` and `meta.page`, with no `withCount` parameter and no Countable profile. A menu counts when its default strategy does, which is what `MultiPaginator::wantsCount()` reports, and a cursor page never counts, as the runtime never counts one.

A relation's example id is relation-level only. The projector never looks the related type up on another server, since a document describes one server. It fills linkage where the related type gives no `Id` example and otherwise defers to that example, so one type's id reads the same wherever it is linked.
