# An action may declare the request bodies it accepts

A raw-input action projected one open `application/octet-stream` body, so a client generator could not tell that an import takes CSV, an image or a typed JSON array, and an integration that negotiates the request `Content-Type` against a list had no way to say so in the document. Action metadata may now implement `DeclaresAcceptedBodies`, and each `AcceptedBody` is one `requestBody.content` entry with its own schema. It is an optional interface rather than a new `ActionMetadataInterface` method so existing integrations keep compiling and project byte-identically. Whether an entry is the JSON:API document or a raw body is a flag on the entry rather than a second input-mode vocabulary, because the action's input mode already says how the integration reads the body. Declared accepted bodies get their own scoped contract tier, `ACCEPTED_BODIES = 11` beside ADR 0173's `RAW_CONTENT = 10`, because contract 10 had already shipped without them and a generator that ignores them emits a client that cannot send the body; a document without them is stamped as before.

An entry with no schema and no `binary` flag first projected as a binary string for every type except `multipart/form-data`, which typed a CSV upload as a file. It now defaults by media-type family: a string for `text/*`, any JSON value for `application/json` and `+json`, an object for the two form types, and a binary string otherwise. The contract stays at 11, because a contract-11 generator already reads a plain string, an empty schema and an object, so only the shape of a document that relied on the old default moves, and the witness declares its entries explicitly.
