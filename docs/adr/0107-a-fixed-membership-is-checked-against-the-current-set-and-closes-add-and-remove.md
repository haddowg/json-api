# A fixed membership is checked against the current set and closes add and remove

`cannotChangeMembership()` lets a client reorder a to-many but not change which members it holds, so a replacement is compared with the current members as a set, ignoring order, and a difference is its own `403 MEMBERSHIP_CHANGE_PROHIBITED` rather than `FULL_REPLACEMENT_PROHIBITED`, because the replacement itself is allowed. Core can't see a data layer's members, so the check takes them as an argument through `GuardsMembershipInterface::assertMembershipUnchanged()`, which `AbstractResource` feeds from an overridable `currentMembers()` on both the relationship endpoint and a whole-resource update, and an adapter writing the association itself calls with the members it holds. A fixed relation reports `allowsAdd()` and `allowsRemove()` as `false`, so `POST` and `DELETE` answer with the existing addition and removal errors and drop out of the OpenAPI document exactly as they do for `cannotAdd()` and `cannotRemove()`. The new code is offered, and the `FIXED_MEMBERSHIP` contract tier stamped, only in a document where some relation reports it through the opt-in `DeclaresFixedMembership` metadata, so a document that never uses the feature keeps its baseline contract and asks no generator to upgrade.
