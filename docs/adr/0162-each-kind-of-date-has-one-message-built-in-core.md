# Each kind of date has one message, built in core

A bad date read differently depending on where it was sent: an attribute said `The value for attribute "publishedAt" is invalid: "last year" is not an RFC 3339 date-time…`, a date range bound got the adapter's generic `This value is not valid.` or `This value is not a valid date.`, and the Laravel adapter's own attribute check said something else again. `DateMessage` now holds one message per kind of date, such as `This value is not a date like 2026-10-01.`, showing the field's or filter's declared example, else a fixed one. The attribute cast, a date range's `invalidBound()`, a comparison or list filter over a date column and both adapters all report it, and the error's `source` says which value it was, so the message names none and reads the same for a bound, a filter value and a nested attribute.

Each message is translatable under its own key below the error's code, such as `ATTRIBUTE_VALUE_INVALID.date_time`, carried as the error's `detailVariant` with the example as its `{example}` context. The key is asked of a resolver through a separate `ErrorDetailVariantResolverInterface`, before the code's own `detail()`, so an existing resolver that only knows codes keeps working and its code-level detail still applies. A field whose format no RFC 3339 keyword names shows 25 October 2026 at 14:30 UTC in its own format, the same value its schema description shows, because a day above 12 cannot be read with the day and the month swapped.

A comparison or list filter over a date field also reads its values as a `DateOperand` carrying the field's kind, set when the filter is resolved, so a database adapter binds a date of the column's type and the in-memory handler compares a day, a time of day or an instant, rather than a raw string against a stored date that never matches.
