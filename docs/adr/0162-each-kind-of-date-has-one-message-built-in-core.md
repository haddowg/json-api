# Each kind of date has one message, built in core

A bad date read differently depending on where it was sent: an attribute said `The value for attribute "publishedAt" is invalid: "last year" is not an RFC 3339 date-time…`, a date range bound got the adapter's generic `This value is not valid.` or `This value is not a valid date.`, and the Laravel adapter's own attribute check said something else again. `DateMessage` now holds one message per kind of date, naming what the client sent the value as and showing a value that would have worked: the field's or filter's declared example, else a fixed one. The attribute cast, a date range's `invalidBound()` and both adapters all report it, so a client reads `filter[published][min] is not an RFC 3339 date-time with an offset, such as 2026-10-01T00:00:00Z.` for a bound and the same sentence about `publishedAt` for an attribute.

The subject of an attribute's message is its pointer below `/data/attributes`, `publishedAt` or `window/startsAt`, because that is already how `ATTRIBUTE_VALUE_INVALID` names the attribute, it stays unambiguous at any depth, and it matches the error's own `source.pointer`. The exception carries the `DateMessage` rather than the finished sentence, and a composite moves it under its own name with `at()`, so the subject is the whole path however deeply the date sits. A field whose format no RFC 3339 keyword names keeps the same message for its kind, with a value in its own format, the one its schema description shows, as the example, rather than a separate message quoting the PHP format string, which a client cannot read.
