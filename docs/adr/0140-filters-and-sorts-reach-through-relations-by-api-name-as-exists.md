# Filters and sorts reach through relations by API name, as an EXISTS

Every value, id and existence filter and `SortByField` take `->through($path)`, naming relations by their API names and the column as a field of the reached type, so the field's `storedAs()`, id encoder and calendar-day rule apply exactly as on that type, and `ThroughPathResolver` resolves the path for every data layer and the OpenAPI projection. Each hop means a related row exists, so a filter is one `EXISTS` that a relation holding nothing never satisfies, even `WhereNull` or `WhereSet` sent `false`, and finding empty relations stays the existence filters' job; a sort reaches through to-one relations only and reads `null` where a relation holds nothing, under the existing nulls rule. The leaf applies through each handler's existing arm (`atLeaf()` with `leafValue()`), so no filter type needs a through-specific arm, and `WhereThrough` and `WhereThroughIn`, whose paths name storage members, are deprecated rather than reimplemented so their behaviour does not move before the next major removes them. An id filter keyed by one of the type's relations reaches through it without a path, since comparing a related resource's ids is what such a key asks for, and keyed `id` or by no relation it keeps comparing the type's own ids; a relation key with another column could mean either, so it is refused.
