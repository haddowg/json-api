# A reference to a named value shape carries its type, with the reference inside an allOf

A field that references a hoisted enum or a `component()` shape used to carry no `type`, while the same field inline carried `type: string` or `type: object` beside its keywords, so moving a field between the two forms made oasdiff and code generators report a type change for values that had not changed. Every field-level reference to a named value shape, and every reference to a `DescribesRawBody` schema, now carries the type the inline form would: the enum's backing type, the shape body's own `type`, and `null` added where the use admits it. The reference is written inside a single-entry `allOf`, the way a `$ref` with an example already was ([ADR 0067](0067-a-ref-carrying-an-example-or-default-is-wrapped-in-a-single-entry-allof.md)), rather than as a bare `$ref` with a sibling `type`. OAS 3.0 tooling, oasdiff's loader among it, drops a `$ref`'s siblings and would never see the type, and one wrapped form for every typed reference doesn't flip between bare and wrapped when a field gains or loses an example.

## Consequences

A nullable use keeps its `anyOf` of the bare `$ref` and `{"type": "null"}` and takes `[<type>, "null"]` on the union. A shape with no single type inline, a `OneOf` or a `Union` that projects a `oneOf`, gets no `type` on its reference either. Core's own structural references, to resource objects, documents, identifiers, relationships, links, meta, errors and responses, are untouched. The `type` restates the component's, so it changes nothing a validator accepts, and a required enum's reference gains no non-empty keyword its component lacks.
