# A relation declared with a foreign key is read through it on every path

A to-many whose parent isn't a database row, such as a singleton served by a custom provider, had nothing to read its members from: the parent model holds no collection, and a data layer that scopes the related query by the parent's own mapping has none to scope by. `HasMany` and `HasOne` take an optional third argument naming the related type's field or to-one relation that holds the parent's id, and a relation declared with one is read as the related rows whose foreign key is a parent's id, by the related type's data layer, on every read path and whatever stores the parent, even when a mapped association exists. The name is resolved against the related type rather than given as a column, so a warm-up check can refuse one that holds no parent id, and the OpenAPI projection doesn't change because the foreign key is a storage detail. A `BelongsToMany` refuses one, since its members live in its pivot rows.
