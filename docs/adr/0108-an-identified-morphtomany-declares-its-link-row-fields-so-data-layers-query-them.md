# An identified MorphToMany declares its link-row fields so data layers query them

The `identifiedBy()` closure maps a parent to every pair at once, so an adapter paging link rows in SQL had to rebuild each row's pair by running the closure over a doctored parent, and fell back to memory whenever a scope hid rows of a member type. `identifiedByRows()` instead declares the row class through `through()` and the row's owner, type and id fields, with an explicit map from stored type to JSON:API type that core never infers, and core derives the members from the rows and sets the rules every data layer runs: a row counts when its type maps to a declared type and it has an id, a narrowed type counts only its admitted ids before the page is cut, and ties break by stored type then id. The fields are fields of the row, not columns, so they mean the same to a Doctrine entity and an Eloquent model, and the closure stays for storage they can't describe, served in memory by `InMemoryLinkRows`, which applies the same rules and so remains the witness adapters are checked against.

The same declaration lets core plan the writes, so a relation declared with `identifiedByRows()` takes no `fillUsing()` and a persister applies a `LinkRowWritePlan` instead: the rows to delete, then the rows that move to temporary positions, then the updated and inserted rows at their final positions with their pivot values, the order `Positions::plan()` gives so a unique owner and position key holds and new rows need no nullable position. A `fillUsing()` on such a relation fails the build rather than overriding the plan, so there is one write path to keep consistent across adapters and the in-memory witness, and a `typeMap` must map one stored value to each declared type so a new row has exactly one value to write.

Narrowing a type a scope may hide needs the parent's stored keys of that type before the page is cut, so core adds `LinkRowKeysInterface` for one key-only read across a batch of parents and `LinkRowQuery::narrowed()` to drive that read, one admission check per guarded type over the batch's keys and `withAdmitted()` per parent in one order. Both take a list of parents, a single parent being a list of one, because adapters load linkage a page of parents at a time, and a per-parent helper would mean a key read per parent or an adapter narrowing by hand.
