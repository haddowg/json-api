# A named shape is one component per differing representation, and each use keeps its own null

A field declared with `component()` projects its value's shape once as `#/components/schemas/<Name>`, with `<Name>Create` and `<Name>Update` only where a write's shape differs from the response shape, because a shape shared by a helper across many fields should give a code generator one type, while splitting every name three ways, as attributes are, would give it two or three identical types for a union that never differs. The component holds the shape and the constraints declared on the named field, and each use keeps its description, example, deprecation, the non-empty keyword of its `required()` and its `null` beside the `$ref`, so fields that differ only in presence or nullability can share one name; a nullable use is the `anyOf` of the `$ref` and `{"type": "null"}`, the form a nullable hoisted enum already takes. A name whose shape differs between two fields, or that the document already generates, fails the projection rather than being renamed, since the author chose the name and a generated client's type names depend on it.

## Consequences

An object written whole, as a list element or inside an undiscriminated `OneOf`, has a different update shape from one an update merges into, so the same named object can't be used both ways under one name. Likewise a `serializeUsing()` use renders its own shape on a read and can't share a name with a declared-shape use, while an `extractUsing()` use renders the declared shape and shares it. The response shape keeps a constraint only when it applies on both writes, which can drop a create-only bound a field written only on create would otherwise show. Standalone projections, such as the request validator's schema and an adapter's exported JSON-Schema documents, have no components to reference and keep the shape inline.
