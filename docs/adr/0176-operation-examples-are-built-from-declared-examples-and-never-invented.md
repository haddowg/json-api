# Operation examples are built from declared examples and never invented

Every operation's request body and success responses, and each shared error response, now carry a whole `example` on their JSON:API media type, built from the examples fields and error descriptors already declare, so the samples a code generator or an MCP tool description quotes cannot drift from the fields. An example mirrors what the server renders rather than what the schema permits: writes carry the writable members (an `id` only where the client-id policy allows one), reads the members a response without a sparse fieldset renders, links come from the first server URL in the server's link form, a collection shows page two with the paginator's own links and `meta.page`, and its total only when a countable collection can be asked for one. An error response holds a single error rather than every code the status can carry, because these examples are quoted in tool descriptions, where a list of every possible `400` is noise. Catalogue order sorts by class name and would show an atomic-batch error for every `400` and a missing relationship for every `404`, so each status names a representative core code, such as `RESOURCE_NOT_FOUND`, and falls back to catalogue order when the server cannot raise it.

When any value an operation's examples need has no declared example, the operation gets no example at all and a `MissingExample` names the operation, type and field. We rejected filling the gap with a type-derived placeholder such as `"string"` or `0`, because a plausible-looking fake teaches a client a wrong value and nothing flags it; a missing example is visible and fixable. The diagnostics come back from `OpenApiProjector::projectWithDiagnostics()` as a `Projection`, leaving `project()` unchanged. An error code that always fills `source` needs an example of that value too, so `ErrorDescriptor` gains an optional `exampleSource` and every core code declares one.

Overrides are optional metadata interfaces, as every later metadata addition has been, so existing integrations compile and project as before apart from the new examples: `DeclaresOperationExamples` maps an operation name (the `operationId` without its type) to `false`/`null` for none or an `OperationExample` replacing the request and per-status responses it names, `DeclaresActionExample` does the same for one action, and `DeclaresExampleGeneration` switches the server off. An override naming an operation the type does not expose fails the projection, so a typo cannot silently do nothing. A part an override replaces or removes is never generated, so it reports no missing example: an override is how a strict export gets past a value the projector cannot build, such as linkage to a type the server does not register.

Examples get a scoped contract tier, `EXAMPLES = 12`, stamped only on a document that carries one. ADR 0167 kept example values out of the contract guard's comparison, and that still holds, but the guard now records whether a media type has an `example` at all, because a generator will read operation examples and one that ignores them emits clients without them.

A composite's children describe its example whenever they render its value, which includes a `computedUsing()` or `extractUsing()` value; only a `serializeUsing()` hook makes the shape the author's and needs the field's own example. Treating every hook as author-shaped had left computed objects without examples even when each child declared one.

Every core error code now declares an `exampleDetail`, checked against the detail its exception renders, so each error example shows one. The catalogue projects that example as a `detail` narrowing on the code's component, which changes the components every document shares, so contract 13 raises `BASELINE` to `CONTRACT` and the `EXAMPLES` tier no longer distinguishes a document.

ADR 0177 adds two opt-in metadata facts the examples read: whether a collection's paginator always counts, and an id example a relation declares for linkage the related type cannot give.
