# A relation authorizer guards the relation data core reaches itself

A relation's `security(read:)` was enforced only at its two endpoints, so the same data still went out as linkage and `included` on any fetch, and a flattened `on()` write, which runs after the body's relationships, could land on a related row the same body had just linked. Core can't evaluate a host's expressions or gates, so a host gives the server one `RelationAuthorizerInterface` answering both questions per parent: a denied read keeps the relationship's links and drops its data, meta and includes (pruned per parent, since a collection's answer varies by row), and a denied flattened write is `403 ACCESS_DENIED`. It rides the resolver like the timezone does, through an opt-in `ProvidesRelationAuthorizerInterface`, so no existing resolver implementation breaks, and with no authorizer nothing changes.
